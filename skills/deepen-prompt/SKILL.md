# 深化题目

输入是当前对话，用户附带的文字作补充；没有对话上下文时，把附带文字当作题目。目标是**更深而不是更大**：从可观察目标与硬约束重新推导，让执行者做对的事、从原始素材出发、以可证伪的 oracle 收尾。「大」指范围扩大，不指篇幅。

## 步骤

开始前读取目标工作区适用的规则。`scratchpad` 使用工作区约定的临时材料目录；没有约定时，在系统临时目录下为本任务建立独立目录，并向用户说明绝对路径。

1. **写起点陈述。** 三行：
   - **目标**：可观察的结果，不写实现方式。
   - **当前方案**：对话中已形成的方案及其关键假设，每条标「已证」或「推断」。
   - **硬约束**：只列来自规则、代码或用户明确要求的约束。

   后续分析只从「目标 + 硬约束」推导；当前方案是对照组，可以被推翻。完成判据：每条假设都带标签，约束都能指出来源。

2. **定专家。** 一行写出角色，含领域、职责、场景三项限定，再加一句「重点判断什么」（如「负责 Unity 棋盘表现与 DOTS 渲染时序的客户端主程，重点判断动画启动条件、渲染缓存有效期和回调副作用」）。跨领域时以主导领域为准。完成判据：角色具体到能推出此人的日常工作清单。

3. **找原始素材入口。** 先用 `git status` 定代码基线：有在途修改时写明以 HEAD 还是当前工作树为准。再做少量只读查询，定位题目背后的原始素材：代码、历史版本、原始数据、日志、issue 原文、规范原文。入口标 `[已读]` 或 `[待读]`；「会导致」「是缺陷」这类推论读过相关实现才算 `[已读]`，含「只」「没有任何」「每次」「不会」的全称结论须读完整个方法或调用链。完成判据：基线已写明，每个入口可复查。

4. **写 a–d。** 每节最多 4 条，每条一句：
   - **a、未被要求的事**：专家会主动做、题目没提、会改变结果的动作，写明不做会错在哪。固定含一条：依赖被改对象的下游消费者（订阅者、调用方、读取该时刻或状态的地方）及其副作用。
   - **b、原始素材入口**：`路径或命令 → 要从中确认什么`，按可信度排序，只列入口，摘要留给执行者自己读。
   - **c、方法与工具**：可直接执行的命令、工具、库与参数。
   - **d、独立证明**：用户与 agent 之外能判定对错的东西，如测试、可复现测量、diff 或计数基线、一手规范、外部基准、真实用户或数据。每条写通过与失败标准；依赖 `[待读]` 的阈值写成「核验 X 后定阈值」。grep 计数只证明引用覆盖，归为静态检查；与旧版本一致只证明无回归，正确性靠配置意图、一手规范或可量化预期值。环境里确实没有时写「缺少 oracle：需要补 X」。

   完成判据：每条可执行；d 至少有一个 oracle 或一条缺口声明。

5. **grill。** 把 a–d 暴露的、只能由用户决定的取舍（范围、行为能否变化、验收标准、交付物）按轮确认：
   - 每轮问完当前的 **frontier**：前置决定已确定的全部问题；答案依赖本轮其他问题的，留到下一轮。
   - 每题格式 `❓ **Qn** - **标题**：正文` 加 `➡️ 推荐答案`，措辞让「是」即接受推荐，题间用 `---` 分隔。
   - 只问会改变任务书「做什么」或「怎么验收」的取舍。能从环境查到的事实自己查，量大时在后台派只读 Explore subagent，只让依赖该事实的问题等待。
   - 用户回答后重算 frontier，提下一轮。

   完成判据：frontier 为空，且用户确认双方理解一致。

6. **写任务书。** 任务书是全新执行者的唯一材料，写到 scratchpad 的 `deepen-<主题>.md`，依次包含：代码基线、起点陈述（当前方案标为对照）、已核实事实、要回答的问题、方法、oracle 与完成判据、边界与交付。
   - 每句追溯到 a–d 或 grill 结论，且改变「做什么」或「怎么验收」；追溯不到的删去。
   - 替换优先于追加：把含糊词换成具体对象、场景与度量（「优化性能」→「在 X 场景测 p95 帧耗时」）。
   - `[待读]` 与推断写成「需先核验：…」，与已核实事实分开。
   - 交付物默认为只读调查：候选方案、证据、各 oracle 结果，写入 scratchpad 的 `deepen-<主题>-report.md`。grill 中用户明确允许改动时才写实施步骤，并将目标工作区要求的派发约束和核验方式写入任务书，让全新执行者无需原对话即可遵守。

   完成判据：只读任务书的执行者能开工，并知道何时算完成；逐句核过前两条。

7. **派发与核验。** 聊天里只给任务书完整路径与三行摘要（目标、交付物、oracle），同一轮派全新 general-purpose subagent 执行，prompt 只给任务书路径。用全新 agent 而非 fork，执行者才脱离原对话对当前方案的锚定。回报后主会话用 Read / Grep / `git status` 独立核验报告与改动，按 d 的 oracle 逐条对照向用户汇报。环境不能派 subagent 时停在任务书落盘，提示用户把它贴进新会话执行。

## 聊天输出格式

步骤 1–5 在同一条回复中给出，结构固定：

```
**专家角色**：…
**起点**：目标 … / 当前方案 …（已证 / 推断）/ 硬约束 …
**a、未被要求的事** …
**b、原始素材入口** …
**c、方法与工具** …
**d、独立证明** …
---
❓ **Q1** …
```
