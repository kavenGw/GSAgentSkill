# 规则沉淀

把本次经验转成下一次任务能读到、能据此改变决策的最小约束。允许结论为“不需改规则”，但不能仅以“已有类似文字”为依据。

## 确定证据与范围

从当前会话确定用户纠正了什么、期望行为是什么，以及原决策在哪一步偏离。核对涉及的当前实现和原生差异，区分本次改动与用户已有改动；不把一次失败推测成普遍原因。

先读目标项目的指令入口、规则索引及相关正文。有规则维护约定时按其确定写入位置。项目惯例留在项目规则中；只有用户明确要求跨项目适用的偏好才进入全局指令。用户只要求评估或草案时，交付判断，不写文件。

## 判断规则缺口

分别检查内容和可达性：

| 现状 | 处理 |
|---|---|
| 缺少有证据支持的可复用决策约束 | 补入最相关的现有规则 |
| 正文正确，但触发词或入口漏掉本次任务类型 | 加强索引或入口指针，正文保持单一权威来源 |
| 能读到，但只教操作方法、未说明何时需要操作 | 补充决策前提和适用边界 |
| 存在冲突、旧示例或过宽要求 | 调和直接相关内容，保留仍成立的契约 |
| 内容明确、入口覆盖，属于未遵循或一次性错误 | 说明实际执行偏差；不靠重复规则制造约束感 |
| 证据不足或仅为本次例外 | 不推广；必要时只询问影响规则边界的缺失信息 |

检查入口时，用原始任务的措辞和当时已知信息判断会读哪些文件。事后知道规则标题，不代表处理原任务时就能发现它。

例如，“文字用哪个赋值 API”没有回答“固定文案是否需要代码赋值”。若项目约定固定文案属于作者场景，应补充这个前提，并让标签节点报错等相关任务能读到它；不能推广成所有 UI 文本都禁止赋值。

## 写入最小有效约束

优先修改已有条目。正文写清决策条件、期望动作和具体后果，必要时保留一个核验过的代码锚点。入口只保留简短判据及阅读指针，避免复制完整正文。

规则要约束导致问题的决策，而非复述单次补丁。区分固定内容与动态内容、项目约定与通用事实、正常路径与真实例外。不要把一次修复变成全库清理、额外审批或每次必跑的审计流程。

涉及删除行为时，关注被删逻辑的职责和剩余消费者：仅为该逻辑服务的模板、缓存、字段或校验，应先核对引用再决定清理。规则沉淀本身不授权修改业务代码；发现遗留项时单独报告，除非原任务已明确授权继续处理。

不为一条约束建立新规则文件；现有结构确无合适落点时，按项目约定扩展并同步索引。保留无关改动，不自动提交、推送或同步其他配置。

## 验证与交付

对拟写规则做一次简短情景核验：

- 原始问题：只凭当时信息，入口能否引导读取，规则会改变哪个决策？
- 相邻合法情况：规则是否仍允许正确操作，避免把真实动态需求误判为冗余？
- 无关情况：是否会误触发或强迫额外工作？

这是边界推演，不称为实测。核对引用路径、代码锚点、相关旧条目和实际差异；若修改 skill 本身，再执行其验证工具。

交付说明：是否需要规则及原因、改动位置、预期阻止的错误决策、仍允许的合法情况。没有修改时说明为何现有内容与入口已足够，以及这次偏差发生在哪里。无需另建复盘报告、计划或测试文件。
